### 3.1 从 88.9% 到 100% 的修复过程

第一次全量评估（21:49）只有 16/18 通过，两条失败用例同源：

| 用例 | 期望意图 | 实际意图 | 耗时 |
|---|---|---|---|
| `company_announcement_count`（贵州燃气发了多少公告）| `[company]` | `[announcement, company]` | 36.9s |
| `company_filtered_by_code`（688728 最近有什么公告）| `[announcement]` | `[announcement, company]` | 233.8s |

**根因**：路由 prompt 里只有"如果是复合问题，选多个"这一条规则，
没有说明什么时候**不该**多选。LLM 倾向于"更全面"，把单一诉求拆成两个 agent。

**修复**：在 prompt 中加入显式判断方法和反例。

```
## 多选原则（重要，宁少勿多）
只有当用户一句话里存在两个及以上彼此独立的问题时，才选多个 agent。
判断方法：能不能把这句话拆成两个各自独立、单独问也成立的句子？

只选一个的例子：
  "贵州燃气发了多少公告"  → 只选 company（统计能力直接给数）
  "688728 最近有什么公告" → 只选 announcement（代码识别在内部完成）
```

**效果**：
- 意图识别 6 条测试全对
- 18/18 通过
- 平均延迟 11.42s → **9.73s**（少调一个 agent + 少一次 LLM 汇总）
- P95 54.74s → **48.91s**

这条经验可以写进简历：**prompt 里的"负面约束"比"正面描述"更能约束 LLM 行为**。

## 四、关键技术决策

### 4.1 为什么用官方 a2a-sdk 而不是 python-a2a

| 对比 | python-a2a（社区） | **a2a-sdk（官方）** |
|---|---|---|
| 版本 | 0.5.4 | **1.3.0** |
| AgentCard | pydantic | protobuf |
| 协议合规 | 部分实现 | **完整实现 v1.0** |
| 能否跑 TCK | 不确定 | **可以** |

### 4.2 为什么用两阶段检索

纯向量检索的余弦相似度区分度太低：

```
query: "回购股份"
  回购公告    → 0.6276
  三季报提示  → 0.2253
  董事会换届  → 0.1560
```

**区分度提升 4 倍**，Top-1 准确率显著改善。

### 4.3 为什么不混用 embedding 模型

```
同一文本跨模型相似度:     0.078
同模型内正确匹配:         0.886
```

**混用会导致检索完全失效**，因此换模型必须清空重建。

## 六、踩过的坑（14 个）

### A2A 协议层（4 个）

1. 方法名是 `SendMessage` 不是 `message/send`
2. 必须带 `A2A-Version: 1.0` 头
3. 同步响应不能直接用 TaskUpdater，要直接 enqueue Message
4. `DefaultRequestHandler` 需要 `agent_card` 参数

### 数据采集层（4 个）

5. **巨潮分页第 150 页回绕到第 1 页**（漏 45% 数据）
6. pageSize 上限固定 30
7. 上金所必须带 `instid` 参数（否则返回全 0）
8. 东方财富对本机 IP 断连，改用新浪（GBK 编码）

### 数据存储层（3 个）

9. **跨模型向量不兼容**（相似度 0.078 vs 0.886）
10. `Decimal`/`date` 不能直接 JSON 序列化
11. LIKE 的 `%` 与参数化冲突，需写成 `%%`

### 文本处理层（1 个）

12. 贪婪正则切不出公司名，要用滑窗子串

### API 额度层（1 个）

13. 额度耗尽会连续失败刷日志（20 万字节），需加熔断

### Web 集成层（1 个）

14. FastAPI 里不能用 `asyncio.run()`，要拆 `arun()` / `run()` 两个入口

### 编排层（1 个，新增）

15. **路由 prompt 缺少"负面约束"会导致意图过度拆分**
    见第 3.1 节，修复后 TSR 88.9% → 100%
